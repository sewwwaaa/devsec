1. Executive Summary & System Overview

Modern software development demands a fundamental paradigm shift from legacy "perimeter-only" security towards an automated, continuous DevSecOps pipeline where security practices are embedded throughout every phase of the Software Development Life Cycle (SDLC). To operationalize these concepts without reliance on commercial cloud subscriptions or complex Kubernetes clusters, our group selected and engineered TaskShield, a multi-component open-source task and note management platform designed around the Node.js/Express and REST architectural style, fully conforming to the criteria in Appendix A of the IE3142 module brief.

TaskShield satisfies all foundational requirements:

  • Componentry: It features two distinctly separated communicating components—a modern browser-facing single-page application (SPA) presentation tier and an asynchronous REST API backend microservice communicating over HTTP/JSON.
  • Containerisation: Each tier contains dedicated Dockerfiles, accompanied by a root docker-compose.yml orchestrating the multi-container topology.
  • Offline Capability: The system runs completely offline on a standard local workstation using SQLite persistent volume storage, requiring zero external internet or paid software licenses.
  • Vulnerability Analysis: Rather than treating security as an afterthought checklist, TaskShield implements deliberately isolated vulnerable proof-of-concept pathways alongside production-grade secure coding remediations, providing verifiable evidence of exploit execution, automated detection, and successful mitigation.

1.2 Technology Stack

  • Presentation Layer: HTML5, CSS3, and modern Vanilla JavaScript (ES6+), served via a hardened Nginx 1.27 Alpine reverse-proxy container.
  • Application Layer: Node.js runtime (v20 LTS) with Express.js microservice architecture, utilizing Helmet for HTTP security header injection, Joi for strict input validation, Bcrypt.js for salt-and-hash password storage, and JSON Web Tokens (jsonwebtoken) for stateless Bearer authentication.
  • Data Layer: SQLite embedded database engine with write-ahead logging (WAL), structured with dedicated tables for user identity, tenant-isolated notes, and an immutable security audit trail.
  • DevSecOps Toolchain: Semgrep (SAST), npm audit & Trivy (SCA/Filesystem), Gitleaks (Secret Detection), Trivy (Container Scanning), OWASP ZAP (DAST), and HashiCorp Vault (Dynamic Secrets Management).

1.3 System Architecture & Trust Boundaries

TaskShield implements defense-in-depth across four distinct trust boundaries:

  • Trust Boundary 1 (Public Internet to DMZ): Separates untrusted public clients and adversaries from the network perimeter. All inbound requests are treated as hostile until validated.
  • Trust Boundary 2 (DMZ / Perimeter Tier): Nginx serves as the reverse proxy on host port 8080. It terminates external traffic, enforces Content-Security-Policy (CSP) and anti-clickjacking headers, and forwards sanitized calls to the internal application network.
  • Trust Boundary 3 (Application Tier): The Node.js Express backend runs on port 5000 within an internal isolated Docker bridge network (app-network). It enforces strict Joi input validation, rate limiting, role-based access control (RBAC), and tenant ownership authorization before routing to business logic.
  • Trust Boundary 4 (Data & Secrets Persistence): The database and secret stores are isolated from direct external access. Secrets are injected at runtime directly into process memory via environment variables or HashiCorp Vault, ensuring zero plaintext secrets reside on disk or within git history.

3. Secure Coding: Exploit-and-Fix Walkthrough (LO2)

This section documents the core technical requirement: demonstrating working exploits against unmodified endpoints, implementing secure code remediations, and proving that the exact same exploit payload is definitively blocked.

3.1 Vulnerability 1: SQL Injection Authentication Bypass (CWE-89)

Unmodified Flaw: Direct string interpolation in authController.vulnerableLogin:

const rawQuery = `SELECT * FROM users WHERE username = '${username}'`;

Exploit Demonstration: Payload {"username": "admin' OR '1'='1", "password": "x"} sent to POST /api/auth/vulnerable-login bypasses password verification and returns HTTP 200 with an admin JWT token.

Secure Coding Fix: Parameterized query binding and Joi alphanumeric validation in authController.login:

db.get('SELECT * FROM users WHERE username = ?', [username], async (err, user) => { ... });

Verification: Re-running the payload against POST /api/auth/login returns HTTP 400 Bad Request (Validation failed), completely blocking the attack.

3.2 Vulnerability 2: Stored Cross-Site Scripting (XSS) (CWE-79)

Unmodified Flaw: Storing raw unescaped HTML in noteController.vulnerableCreateNote.

Exploit Demonstration: Payload containing <script>alert(1)</script> and <img src=x onerror=...> is persisted in the database with status HTTP 201.

Secure Coding Fix: Integrated sanitize-html in noteController.createNote with strict tag whitelist and Helmet CSP headers.

Verification: Re-running the payload against POST /api/notes strips all dangerous script tags and event handlers, storing clean text.

3.3 Vulnerability 3: Broken Object Level Authorization / IDOR (CWE-639)

Unmodified Flaw: Querying notes by ID in noteController.vulnerableGetNoteById without checking caller identity.

Exploit Demonstration: User Bob (ID: 3) accesses GET /api/notes/demo/bola/1 and exfiltrates Alice's confidential budget record (HTTP 200).

Secure Coding Fix: Ownership verification guard in noteController.getNoteById:

if (note.userId !== req.user.id && req.user.role !== 'admin') { return res.status(403).json(...); }

Verification: Bob repeats the request against GET /api/notes/1 and is blocked with HTTP 403 Forbidden, triggering an entry in audit_logs.

3.4 Vulnerability 4: Hardcoded Fallback Secret & JWT Token Forgery (CWE-798)

Unmodified Flaw: Verifying tokens against hardcoded fallback constant secret123 in authController.vulnerableJwtValidate.

Exploit Demonstration: Attacker mints an offline token with secret123 and role admin. Endpoint accepts token with HTTP 200.

Secure Coding Fix: Mandatory dynamic 256-bit secret loaded via environment variables or HashiCorp Vault.

Verification: Attacker presents the forged token to GET /api/admin/audit-logs; cryptographic verifier rejects the signature with HTTP 403 Forbidden.

4. CI/CD Pipeline Design & Security Automation (LO3)

The TaskShield CI/CD pipeline is implemented using GitHub Actions (.github/workflows/devsecops.yml). Triggered on every push and pull request, the workflow enforces four automated security gates:

  • Gate 1 (SAST): Semgrep Action scanning code against OWASP Top 10 patterns.
  • Gate 2 (SCA): npm audit --audit-level=high and Trivy Filesystem scanning dependencies for known CVEs.
  • Gate 3 (Secrets): Gitleaks Action scanning git history with .gitleaks.toml to block committed keys.
  • Gate 4 (Container Security): Aqua Security Trivy scanning the built Docker image with --severity CRITICAL --exit-code 1.
  • Extra Credit (DAST): OWASP ZAP baseline scan executing dynamic security header and runtime checks against running containers.

Evidence of Automated Pipeline Gate Failure

In .github/workflows/devsecops-failure-demo.yml, Gate 2 is configured with zero tolerance for high-severity package vulnerabilities. When high-severity transitive vulnerabilities are detected: 

Run npm audit --audit-level=high
npm error 7 vulnerabilities (2 low, 4 high, 1 critical)
npm error Process completed with exit code 1.
##[error] Process completed with exit code 1.

Because the command exits with code 1, GitHub Actions terminates the workflow immediately, preventing vulnerable artifacts from proceeding to production.

5. Secrets Management Approach

TaskShield strictly enforces zero plaintext credentials in git history. All sensitive configurations are managed through:

  • Template-only Repo Storage: Real credentials are excluded via .gitignore; only .env.example is committed.
  • CI/CD Masking: GitHub Actions Encrypted Secrets (${{ secrets.JWT_SECRET }}) mask values in build logs.
  • HashiCorp Vault Dynamic Injection: In production, TaskShield connects to Vault's HTTP API (/v1/secret/data/taskshield) to lease dynamic secrets directly into process memory without touching disk.

6. Industry Trends & Case Study Analysis

Modern DevSecOps emphasizes Shift-Left practices and the automated generation of a Software Bill of Materials (SBOM) to secure software supply chains.

Case Study: CircleCI Security Incident (2023)
In January 2023, CircleCI suffered a breach where an engineer's stolen session token allowed adversaries to access build systems and decrypt customer environment variables.

Lessons Applied to TaskShield:

  1. Dynamic Ephemeral Secrets: Using HashiCorp Vault dynamic leases rather than static persistent credentials in runners.
  2. Short Token Lifetimes: Configuring 15-minute JWT expiration windows (JWT_EXPIRES_IN=15m) to mitigate token theft.
  3. Container Hardening: Enforcing Trivy scans, non-root execution (USER node), and no-new-privileges:true flags.

7. Reflection & Future Improvements

  • Policy-as-Code: Integrate Open Policy Agent (OPA) / Conftest to enforce declarative container policies across repositories.
  • Mutual TLS (mTLS): Deploy HashiCorp Consul service mesh to encrypt inter-container communication between Nginx and Express.
  • Automated DAST Fuzzing: Integrate full OpenAPI (Swagger) schema exploration into OWASP ZAP in CI.
